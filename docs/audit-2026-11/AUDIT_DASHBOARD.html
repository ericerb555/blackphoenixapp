The one failure mode

Nearly every finding across all twelve documents is the same shape: a failure that returns a success-shaped answer. A table that never existed, queried by a client that discards the error. An RPC that never existed, so a dead feature merely looks unused. A permission denial that returns an empty list, indistinguishable from an empty result. A toast that says “Saved” because nothing checked the response. A dependency audit that returned {} because the tool could not read the lockfile — which is the one that caught the auditor.

That is why the method had three rules: a control is not verified until a request proves it; probe as an outsider, not as the author; and an absence is not a presence.

Evidence, by what kind it is

The brief was explicit: never count an untested item as passing. These three columns are that rule made visible — and the third one is the reason this audit does not claim full coverage.

Measured a request proved it

A probe, a query, or a production log line.

  • 14 pass / 1 fail / 3 skip — credential-free production probe, re-run today
  • 1,304 auth-wall refusals in 24h, none report-only
  • 20× 403, 6× 404 of 27 guarded routes probed as a real non-staff customer
  • permission denied (42501) on the KV store for both anon and a signed-in customer
  • 4,111 tests pass, 0 fail
  • Cart IDOR: 200 → 404, before and after
  • 5 advisories in prod deps — 1 low, 4 moderate, 0 high

Read only source, not behaviour

Intent established. Behaviour inferred.

  • The orders-by-email deny branch — it returns an empty list, so from outside it is indistinguishable from an empty history. Only the code shows the comparison happens.
  • outboundGuard.ts gates outbound fetches — not probed (OWASP A10)
  • Nine SECURITY DEFINER functions reasoned about, then spot-checked anonymously

Untested recorded as a gap

Not a pass. Named so it cannot be mistaken for one.

  • The WAF’s own rules. Every probe here bypassed Cloudflare by design, so nothing in this audit verifies it
  • Cross-tenant isolation between two staff accounts at different companies
  • Restoring from the nightly storage backup. The job runs; a restore has never been attempted
  • Load behaviour, and the public POST paths that have no limiter and do write records
  • Payment flows
  • Nine autonomous cron jobs

Order of work

Numbered because it is a real sequence: batch 2 is the prerequisite for verifying any of the rest, and batch 3 has a wrong order of operations baked into it today.

  1. Stop the application lying

    All four P1s. Every one is a deletion or a one-line rewire: the member-added toast, the delete button that cannot work, the invented financial seed, the self-manufacturing alerts panel.

    ~half a day · W-3, W-1, W-2, I-1, L-3

  2. Make denials visible

    One console.warn in the staff guard, the same on the silent deny branch, and a server-side home for the security event log. Until this lands, no fix in this plan can be confirmed to be holding in production.

    ~3 hours · L-1, D-2

  3. Header the backup cron, then enforce the origin lock

    In that order. Reversed, the cron keeps firing, the function keeps answering 403, and the backups stop with no error anywhere. Add a restore drill while you are here — a backup nobody has restored from is a hypothesis.

    ~3 hours · A-2

  4. Classify the eleven tables that never existed

    Nothing deleted automatically. Complete the stakeholder and portals features or disable them; likely remove the four that duplicate what KV and app_metadata already hold; and complete security_audit_log, because it is the one on the list that is a security control.

    1–3 days · D-1

  5. Triage the scanner output

    44 handlers that are only a message, 85 that claim success without reaching the server, 188 controls with no handler, 25 authorization leads. This is scanner output, not a defect list — treating it as findings would be the brief’s warning in the other direction.

    ~4 days · triage before fixing

  6. Harden

    Gate the panel fetches on a session (highest-value P3, and it must precede enabling IP reputation or the dashboard bans its own operator). Pin one Hono and one supabase-js version. Revoke anon execute. Retention policy.

    ~1 day · A-1, DEP-1, D-3, L-2, A-3, S-1, F-2, I-3, L-4, AI-2
Waiting on the owner

Four decisions that are not mine

Three of these block verification rather than fixes.

  1. Was the GitHub PAT revoked, or only deleted? It was reported deleted on Tuesday. This is the only finding in the audit where a credential may still be live, and it needs one yes or no.
  2. Test accounts, one per role. Cross-tenant isolation between two staff accounts at different companies is the largest untested area in the security audit; it cannot be probed with one customer token.
  3. One hostile prompt-injection payload. Designed and unsent. The fencing looks sound and the blast radius is bounded by server-side pricing, but nothing proves it.
  4. A staging environment. Load and payment testing were skipped because production is the only environment, and the public application forms write real records.

The deliberate security work holds up to measurement. The risk sits where something quietly does nothing.

RLS on 39 of 39 tables, with denial proven at the GRANT level against two separate identities. No secret in the browser bundle, confirmed twice by different methods. Authority read from app_metadata — the bag an account cannot write for itself — after eleven checks were found reading the one it can. The auth wall enforcing in production. A closed action registry for the AI agent with a real, asymmetric kill switch.

Against that: four P1 findings, every one of them the application telling an operator something untrue. Half a day clears all four, and that is where the plan starts.
